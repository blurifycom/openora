# Agent instructions

This repo is a downstream igaming operator built on the OSS platform (`@openora/*`). Every per-tool instruction file (`AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, `.codex/config.toml`) and the subagent and command mirrors are generated by [rulesync](https://github.com/dyoshikawa/rulesync) from `.rulesync/`. Edit the source, run `pnpm gen:agents`, never hand-edit a generated file.

Sibling rules (load on demand; don't reopen settled questions):

- `conventions` - the always-on code standard, with a table routing each kind of change to its deep-dive file in `docs/standards/`.
- `oss-boundaries` - never patch `@openora/*` in place; core changes go through an OSS worktree; enforced import/module boundaries.
- `e2e-conventions` - Playwright specs against the real stack, fixtures, page objects, API specs.
- `db-conventions` - SQL / Drizzle rules for the tables an overlay owns.
- `frontend-conventions` - React/UI rules for the operator's apps and shared UI package.

## Agent files: generated from the template, or owned here

Most of `.rulesync/` (skills, subagents, commands, hooks, the shared rules) and `docs/standards/` are generated: `pnpm install` renders them from `@openora/create`'s consumer template at the pinned `@openora/*` version, using the variables in `.rulesync/sync.json`. They are gitignored via the managed `synced-agents` block in `.gitignore`, so they never appear in a diff and cannot drift - editing one locally is pointless, the next install overwrites it. Change it upstream in the template instead. This repo owns and tracks the rules and skills the template does not ship, plus the `consumerOwned` overrides in `.rulesync/sync.json`; operator-specific facts belong there or in `sync.json` vars.

## How you work here

- Before acting on a non-trivial request, and before delegating, run the `enhance-prompt` skill on the raw ask. Skip it only when the ask is already precise. Subagents act on the brief they are handed; they do not re-enhance it.
- Your human-facing job is gathering requirements until a stranger could build from them; the `start` / `enhance-intent` MCP tools give the checklist. Then delegate to the subagents (`expert` -> `builder` -> `qa`) and return to the user only for decisions they alone can make.
- A task that names a ticket key starts by reading the whole ticket per `docs/agents/issue-tracker.md`. Never write to the tracker unless the user asks for that exact write.
- `pnpm verify` on the committed tree is the gate before a merge/pull request; the `guard-mr` hook refuses to open one until it has passed on HEAD.

## What this repo is

- `apps/api/` - thin Hono + oRPC API entry, your own `extensions.config.ts`.
- This is a headless API consumer; build your frontend in its own repo and consume the API over HTTP via `@openora/react`.
- `@openora/*` packages are pinned npm dependencies.
- New behaviour, a vendor swap or a mounted page: the `create-plugin` skill picks the generator.
