# Wallet Module - AGENTS.md

## What this module does

Manages user balances, deposits, and withdrawals. Ships with `MockPaymentAdapter` as the default `PAYMENT_ADAPTER` binding - a synthetic PSP that returns `{ externalId, status: 'completed' }`. Emits domain events on completed transactions. Every user gets one wallet per system; money columns are Postgres `NUMERIC` via drizzle `decimal({ precision: 18, scale: 8 })` (`wallet.balance`, `wallet_transaction.amount`, `auto_withdrawal_rule.threshold`) - a decimal STRING in TS, never a float, never a scaled integer. Scale 8 covers both fiat (2dp) and crypto (BTC-level 8dp precision) without a per-asset rescale table. Balance mutations run as SQL numeric arithmetic (`sql\`${wallet.balance} + ${amount}::numeric\``); see ADR-0029.

`PAYMENT_ADAPTER` covers two vendor shapes (see `docs/adapters/payment.md`): a synchronous PSP (`processDeposit`/`processWithdrawal` return an already-terminal status) and an address-based/async custody vendor (`issueDepositAddress` + `parseWebhook`, driving inbound deposits and delayed withdrawal settlement through `POST /wallet/webhook`).

Withdrawals run through a back-office approval queue: a player `withdraw` HOLDS funds (balance debited at request time) and creates a `pending` transaction. A Payments Manager approves (status -> `processing`, sent to the PSP/Fireblocks rail) or rejects with a mandatory reason (status -> `rejected`, held funds returned). Status lifecycle: `pending` -> `processing` -> `completed`; reject -> `rejected`. Rail is derived from the currency (`BTC`/`ETH`/`USDT` -> `fireblocks`, else `psp`).

Async vendor settlement: a synchronous PSP's `processWithdrawal` returns an already-terminal status and `processing` -> `completed`/`failed` happens immediately (`settleApproved`, unchanged). An async/custody vendor returns a non-terminal status (eg `'submitted'`) - the transaction stays `processing` and `WalletService.reconcileWithdrawalStatus(event)` performs the eventual `processing` -> `completed`/`failed` transition, driven by `POST /wallet/webhook`. `reconcileWithdrawalStatus` is idempotent: it no-ops on a row that isn't currently `processing` (already terminal, or a stray webhook for an unmatched/not-yet-approved row).

## Routes

| Method | Path                                       | Auth                         | Description                                                        |
| ------ | ------------------------------------------ | ---------------------------- | ------------------------------------------------------------------ |
| GET    | /wallet/balance                            | player                       | Returns balance + currency                                         |
| POST   | /wallet/deposit                            | player                       | Credit funds, emit domain event                                    |
| POST   | /wallet/withdraw                           | player                       | Hold funds, create a `pending` withdrawal                          |
| GET    | /wallet/transactions                       | player                       | Last 100 transactions for user                                     |
| GET    | /wallet/transactions/{userId}              | admin `transaction:view`     | Backoffice: any player's transaction ledger                        |
| GET    | /wallet/withdrawals                        | admin `withdrawal:view`      | Filterable, paginated withdrawal review queue                      |
| POST   | /wallet/withdrawals/{withdrawalId}/approve | admin `withdrawal:approve`   | Approve -> `processing`, send to PSP/Fireblocks                    |
| POST   | /wallet/withdrawals/{withdrawalId}/reject  | admin `withdrawal:reject`    | Reject (mandatory reason) -> `rejected`, return funds              |
| PUT    | /wallet/auto-withdrawal-rules/{userId}     | admin `withdrawal:auto-rule` | Upsert a per-player auto-withdrawal threshold                      |
| GET    | /wallet/auto-withdrawal-rules/{userId}     | admin `withdrawal:auto-rule` | Read a player's auto-withdrawal rule (or null)                     |
| DELETE | /wallet/auto-withdrawal-rules/{userId}     | admin `withdrawal:auto-rule` | Remove a player's auto-withdrawal rule                             |
| POST   | /wallet/deposits/address                   | player                       | Get-or-create a deposit address for `{ currency }`                 |
| POST   | /wallet/webhook                            | M2M (no session)             | Payment-vendor webhook: deposit credit / withdrawal reconciliation |

Player routes require an authenticated caller (verified better-auth session via `getUserId`, ADR-0019). The `withdrawals.*` admin routes call `adminGuard.assert(context, 'withdrawal', '...')` as the first line; the queue lists username + KYC status via the `ADMIN_USER_DIRECTORY.lookupPlayers` port (never reading the player/profile tables directly). Queue filters: `status` (omit for all statuses, not pending-only), `currency`, `rail`, `minAmount`/`maxAmount` (decimal strings), `kycStatus`, `dateFrom`/`dateTo`, plus `page`/`limit`. `riskTags` are DB-backed heuristics (not a risk engine): `large_amount` (amount >= 5000) and `high_frequency` (>= 3 withdrawals for the wallet in the trailing 24h, one batched grouped-count query).

KYC withdrawal gate: when `platformConfig.kyc.gateWithdrawals` is true, `withdraw()` fails closed unless the player's KYC status is in the pass-set (`verified` or `manually_overridden`), throwing `KycRequiredError` (maps to CONFLICT). The status is read through the existing `ADMIN_USER_DIRECTORY.lookupPlayers` port - no new cross-domain coupling. Off by default.

Auto-withdrawal: after the hold commits, `withdraw()` runs a strictly fail-closed evaluator (`maybeAutoApprove`) that decides WHO approves the withdrawal - the system or the manual queue - never whether the request itself succeeds. It NEVER throws out of `withdraw()`; any error or ambiguous branch leaves the row `pending`. On eligibility it reuses `flipToProcessing`/`settleApproved` directly (the same two-phase sequence the manual approve uses: `processing` commit -> PSP call outside the tx -> `completed`, or refund on PSP failure), with `reviewedBy = null` and `reviewReason = 'auto-approved'` as the system-actor marker. Only the daily-cap check runs under the per-user advisory lock (atomic with the `processing` flip); threshold/KYC/risk/velocity gates run before the lock. All gates must hold: `platformConfig.autoWithdrawal.enabled`; a resolved positive threshold for the withdrawal's RAIL (per-player `auto_withdrawal_rule` wins over the global rail threshold - `autoWithdrawal.fiatThreshold` for fiat, `autoWithdrawal.cryptoThreshold` for crypto) with `amount <= threshold` (compared via `moneyToNumber()`, the sanctioned decimal-to-JS-number conversion point for this heuristic, never for a ledger write); KYC status in the pass-set INDEPENDENT of `kyc.gateWithdrawals` (missing directory/summary => pending); no active tag intersecting `autoWithdrawal.excludeRiskFlags` (resolved via the `PLAYER_TAGS` port - unbound while flags are configured => pending); no `large_amount`/`high_frequency` heuristic; and the trailing-24h auto-approved `dailyCapAmount`/`dailyCapCount` not exceeded. Every auto-approval writes an `AUDIT_WRITER` entry (`actorType: 'system'`, `action: 'wallet.withdrawal.auto_approved'`) capturing the full rationale (threshold + source, KYC status, risk tags evaluated, caps used) BEFORE the PSP call, so the AML/SAR trail survives a PSP failure. Rule set/delete write `wallet.auto_withdrawal_rule.set`/`.deleted` admin audit entries. Off by default.

Before the `PLAYER_TAGS` risk-flag read above, `withdraw()` (still inside its own withdrawal transaction, right after the guarded debit) calls `await this.tagEvaluationCommands.evaluateWithdrawalRequested(txn, { userId, amount })` when the `TAG_EVALUATION_COMMANDS` port is bound (optional, resolved lazily via `c.has(...)` in `plugin.ts` - same reason as `PLAYER_TAGS`: wallet can't `dependsOn: ['tag']`, that would cycle). This is what makes the risk-flag exclusion gate correct: `EventBus.emit('wallet.withdrawal.requested', ...)` is fire-and-forget and never awaited by the emitter, so without this synchronous call `maybeAutoApprove` could read `PLAYER_TAGS` before the tag module's async event handler has assigned `withdrawal_review`, auto-approving a withdrawal that should have been excluded. `evaluateWithdrawalRequested` runs on the withdrawal's own `txn`, so a `withdrawal_review` assignment it makes commits atomically with the withdrawal request row - guaranteed visible by the time the transaction returns and the risk-tag read runs. An unexpected error from it propagates and aborts the whole withdrawal (fail-closed on the review gate itself, separate from `maybeAutoApprove`'s own fail-closed-to-pending behavior). See `pam/tag/AGENTS.md` for the port's tag-module side.

BF-211: crypto auto-approval is threshold-driven, the SAME mechanism and the SAME gates as fiat (KYC-approved-status, risk-tag exclusion, large-amount/high-frequency heuristics, daily caps) - it is no longer a blanket rail-based hard stop. What keeps it safe is that `autoWithdrawal.cryptoThreshold` is absent by default: an unset/zero threshold resolves to "never auto-approve", so an operator must explicitly opt in with a positive value - upgrading to this version never silently activates crypto auto-approval on an existing deployment. The per-player `auto_withdrawal_rule` override is a single global column (not rail-aware) - it overrides whichever rail the withdrawal is on; there is no separate per-player fiat vs crypto override today.

Client-supplied idempotency: `deposit` and `withdraw` accept an optional `idempotencyKey` (uuid). `wallet_transaction.idempotency_key` carries a partial unique index scoped to `(wallet_id, idempotency_key)` - a wallet is 1:1 with its user, so this is equivalent to scoping on userId. A matching key returns the ORIGINAL stored transaction (same response shape, no second insert, no re-emitted domain event) - a REUSED key with a DIFFERENT amount is rejected as `IdempotencyKeyReuseError` (CONFLICT) instead of silently replaying the wrong result. The insert uses `onConflictDoNothing()` (unqualified - the table's only unique index is the partial idempotency one); a concurrent race on the index makes the loser's insert a no-op (never aborts the transaction) and it re-reads the winner's already-committed row instead of erroring. No key = unchanged behavior (plain insert, no dedup).

`deposit` checks for a replay BEFORE calling the PSP (a plain pre-transaction read) so the common retry case (client resends after a timeout) never re-charges. This pre-check is NOT itself race-safe: two concurrent first-attempts for the same brand-new key can both miss it and both reach the PSP - that narrow window is accepted (the ledger write itself still never double-credits, via the `onConflictDoNothing` guard above).

Rate limiting: `deposit` and `withdraw` consume a per-user budget (30/min, keyed `wallet-mutation:<userId>`) via the `RATE_LIMITER` port before doing any work - exceeding it throws a 429 (`TOO_MANY_REQUESTS`) carrying `retryAfterMs`. This guards a runaway client, not fraud (idempotency + the ledger guard cover correctness); an overlay rebinds `RATE_LIMITER` to a Redis backend for cross-replica coordination.

Deposit addresses: `POST /wallet/deposits/address` (`{ currency }` -> `{ address, currency }`) is `getOrCreateDepositAddress` - checks `wallet_deposit_address` first (unique on `(userId, currency)`) and returns the stored row; only calls `payment.issueDepositAddress` on a miss, persisting the result (`onConflictDoNothing` + re-read on a concurrent race, same pattern as the idempotent transaction insert below). Throws `DepositAddressUnsupportedError` (CONFLICT) when the bound `PaymentAdapter` doesn't implement `issueDepositAddress` (eg a fiat-only PSP).

Payment webhook: `POST /wallet/webhook` is an unauthenticated M2M route (no admin session) mirroring `compliance`'s `kycWebhook` route exactly - verifies `context.rawBody` against `PaymentWebhookVerifier.verify(rawBody, headers)` (fail closed on a missing body/signature), then `paymentAdapter.parseWebhook?.(rawBody, headers)`. A `kind: 'deposit'` event resolves `wallet_deposit_address.address` -> `userId` (unknown address: logs and no-ops, never throws past the webhook boundary) and credits the wallet via `creditDepositByAddress` - idempotent on the vendor's `externalId`, stored as `wallet_transaction.providerRefId` (now a partial UNIQUE index, `onConflictDoNothing` + re-read on conflict - a stronger DB guard than a plain existence check, per the money-critical-path convention). `destinationAddress`/`txHash` are stored on the new typed columns. `wallet.deposit.completed` emits only on the actual credit, never on a replay. A `kind: 'withdrawal'` event calls `reconcileWithdrawalStatus` (see the async-vendor-settlement paragraph above).

## Extension points

- **Ports**: `PaymentAdapter` lives in `@openora/core/contracts` and is passed into `WalletService` (the constructor takes a `PaymentAdapter`; `plugin.ts` resolves `PAYMENT_ADAPTER` from the container). The default binding is `MockPaymentAdapter` (bound in `src/plugin.ts`). Beyond `processDeposit`/`processWithdrawal`, the port has two OPTIONAL methods for an address-based/async vendor: `issueDepositAddress(userId, currency)` and `parseWebhook(rawBody, headers)` (returns a `PaymentWebhookEvent` - `{ kind: 'deposit', address, amount, currency, txHash, externalId }` or `{ kind: 'withdrawal', externalId, status }` - or `null`). Implement them for a real PSP/custody vendor and override the binding via an overlay plugin; see `docs/adapters/payment.md`.
- **Events emitted** (all `amount` a decimal string + `currency`; v2 - see `domainEventVersions`):
  - `wallet.deposit.completed` - `{ userId, amount, currency, transactionId }` (also emitted by `creditDepositByAddress` on an inbound webhook credit, never on a replay)
  - `wallet.withdrawal.requested` - `{ userId, amount, currency, transactionId }` (player held funds, status `pending`)
  - `wallet.withdrawal.approved` - `{ userId, amount, currency, transactionId, adminId }` (status `processing`, sent to PSP)
  - `wallet.withdrawal.rejected` - `{ userId, amount, currency, transactionId, adminId, reason }` (held funds returned, status `rejected`)
  - `wallet.withdrawal.completed` - `{ userId, amount, currency, transactionId }` (vendor confirmed - synchronously via `settleApproved`, or asynchronously via `reconcileWithdrawalStatus`'s webhook path)
  - `wallet.withdrawal.failed` - `{ userId, amount, currency, transactionId, adminId }` (vendor rejected; held funds returned, status `failed`) - only emitted when `adminId` is set (a manual/auto-approve settlement); a webhook-driven failure via `reconcileWithdrawalStatus` refunds and marks `failed` but has no admin to attribute, so it skips this event (same precedent as the system auto-approve path)
  - All are recorded by the `audit` add-on (`SUBSCRIBED_TOPICS`); the `notifications` add-on subscribes to `approved`/`rejected` to notify the player.
- **Ports consumed**: `ADMIN_USER_DIRECTORY` (`lookupPlayers` for queue enrichment + auto-approval KYC), `ADMIN_GUARD` (admin route authz), `PLAYER_TAGS` (optional; auto-approval risk-flag exclusion, bound by the `tag` module), `TAG_EVALUATION_COMMANDS` (optional; synchronous withdrawal_review evaluation on `withdraw()`'s own tx, bound by the `tag` module - see above), `AUDIT_WRITER` (required; auto-approval + rule-change audit trail - the module `dependsOn: ['identity', 'audit']`), `PAYMENT_WEBHOOK_VERIFIER` (webhook signature verification).
- **Ports provided**: `WALLET_COMMANDS` (`WalletCommandsService`) - other modules move money in the wallet WITHIN their own db transaction, without importing wallet tables (ADR-0010/0016). `debit(tx, { userId, amount, type })` and `credit(tx, { userId, amount, type })` both write a `completed` `wallet_transaction` ledger row (internal settlement, no provider ref) so gameplay shows in transaction history. `type` is a `WalletTransactionType` (`bet`/`win`/`loss`/`bonus`/`tip`/...). Both reject a non-positive `amount` - EXCEPT `type: 'loss'`, which is informational: the stake already left the wallet at `bet` time, so a loss writes a 0-amount row and never touches the balance. `debit` returns `{ ok: false, available }` on a shortfall (guarded conditional UPDATE, concurrency-safe, new balance read back from the DB via `.returning()`); `credit` fails closed with `{ ok: false, reason: 'wallet not found' }` rather than creating a wallet.
- **Routes**: `src/router/index.ts`
- **UI slots**: none yet

## Ports

`PaymentAdapter` (symbol `PAYMENT_ADAPTER`, from `@openora/core/contracts`) - the swap seam for a real PSP or custody vendor. `WalletService` injects it and calls it on every money movement: `deposit()` calls `processDeposit(amount, currency, metadata)` BEFORE crediting the balance, and `withdraw()` (via `settleApproved`) calls `processWithdrawal(...)` after the balance check and before debiting. The returned `externalId` is stored on the transaction's typed `providerName`/`providerRefId` columns. The default binding is `MockPaymentAdapter` (returns `{ externalId, status: 'completed' }` - always terminal, so `settleApproved` finalizes immediately). An async vendor returns a non-terminal `status` instead; see the async-vendor-settlement paragraph above.

`PaymentWebhookVerifier` (symbol `PAYMENT_WEBHOOK_VERIFIER`) - verifies the `POST /wallet/webhook` route's inbound bytes. The default binding, `HmacPaymentWebhookVerifier` (`adapters/hmac-payment-webhook-verifier.ts`), recomputes an HMAC-SHA256 over the raw body against the `x-payment-signature` header (case-insensitive lookup, `sha256=` prefix tolerated, timing-safe compare), keyed by `PAYMENT_WEBHOOK_SECRET`. Fails closed when the secret is unset, the header is absent, or the body wasn't captured.

To use a real vendor, implement `PaymentAdapter` under `adapters/<vendor>/` and bind it (plus a matching `PaymentWebhookVerifier` if the vendor doesn't use HMAC-SHA256) in an overlay plugin that loads AFTER the wallet module in `extensions.config.ts` - last registration to each token wins, so the overlay's binding overrides the default with no fork:

```ts
ctx.provide(PAYMENT_ADAPTER, () => new CustodyPaymentAdapter());
```

## Do

- Add business logic to `service/wallet.service.ts` (inject `DrizzleService` from `@openora/core/server`; query via `this.drizzle.db.select().from(wallet).where(eq(...))`)
- Add or edit `pgTable` defs in `src/schema/index.ts` (tables: `wallet`, `wallet_transaction`, `auto_withdrawal_rule`, `wallet_deposit_address`), then run `pnpm regen`
- Implement `PaymentAdapter` in `adapters/<vendor>/` for real payment processing (a synchronous PSP needs only `processDeposit`/`processWithdrawal`; an address-based/async vendor also implements `issueDepositAddress`/`parseWebhook`)
- Emit cross-module events via `EventBus` - never import other modules directly

## Don't

- Import from other modules directly
- Throw framework HTTP errors from services - throw domain errors instead
- Edit the generated migrations under the module's `drizzle/migrations/` by hand - the source of truth is `src/schema/index.ts`
- Use floating-point for money calculations - money columns are `decimal()`/`NUMERIC` (`balance`, `amount`, `threshold`), a string in TS; mutate/compare via SQL numeric ops, never JS math (ADR-0029)
- Add inline Zod schemas in the router - all schemas live in `schemas/` or the contract

## Done when

- `pnpm verify` passes (typecheck + lint + boundaries + module-shape + tests).
- `list-routes module=wallet` shows the new/changed route(s) (e.g. `wallet.deposit`).
- No `boundaries/dependencies` lint errors (no cross-module code imports; read other domains' tables only via the `@openora/core/<domain>/schema` subpath).
- If you changed the `PaymentAdapter` contract, `pnpm regen` then check `docs/catalog.json` shows the `PAYMENT_ADAPTER` seam still wired.
- New tables: added to `src/schema/index.ts`, `pnpm regen` run, migration committed.
