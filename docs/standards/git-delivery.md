# Git and delivery

Detail for the delivery lines in `conventions`. Read this before committing, opening a PR, or writing a commit message.

- **Conventional commits, enforced** (commitlint on commit + CI). Types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `perf`. The scope is a workspace-derived `scope-enum` (module dirs, apps, plus `ci`/`deps`/`rules`/`repo`/`tooling`); an unlisted scope fails - check with `pnpm commitlint --from HEAD~1` or omit the scope. `feat(wallet): atomic debit command port`
- **Subject must start lowercase** (`subject-case`), acronyms included - write `feat(pam): kyc status filter`, not `KYC`. This applies to the **PR title too**: squash-merge derives the `dev` commit message from the PR title, which local commit hooks never lint - an uppercase title lands a failing commit on `dev`.
- **One ticket = one PR, however big.** Never split a ticket by size; splitting is a person's call, made by creating sub-tasks. Stage files explicitly; never `git add -A` with foreign changes in the tree.
- **No changeset in a feature or fix PR.** Do not run `pnpm changeset` or add `.changeset/*.md` alongside code. Changesets are written in their own PR once the work has landed and the release is being prepared, so the bump and summary describe the final state, not every iteration.
- **Green before review:** `pnpm verify` passes; `pnpm regen` after any contract/schema change.
- **Branch off `dev`; never commit directly to `dev`/`stage`.** Promotion chain `dev -> stage` + release tags. Never push without an explicit per-action confirmation, except the branch `/ship` opens its PR from.
- **PR description is a review pack** (`docs/standards/skills/delivery.md` step 9) a reviewer approves from without reading the diff: the bare ticket key, one summary line, the generated "Touches:" line, then the 14 slots of `.github/pull_request_template.md` in order, every one open as a `##` heading, `N/A: <reason>` in place when it does not apply (never for slots 1 and 3 on a money, KYC, responsible-gambling or authz change: each decision names its owner, slot 3 adds "Not covered:", "Revert leaves:" and "Dropped findings:"): 1 Decisions made, 2 Origin (a fix) or Why (docs, deps, tests, tooling; at most three bullets), 3 How it was checked (the hostile cases tried, never green or a test count), 4 Env, 5 Consumer impact, 6 Related PRs, 7 Flow (Request path, Event flow, Pipeline), 8 Data model, 9 Migration, 10 Trace (one per changed endpoint, Queries and indexes), 11 Performance (Load, Measurement), 12 Evidence (Video table Flow | Before | Now | AC, Screenshots before | after, Sample output), 13 Business logic (and State machine), 14 Endpoints and permissions. Size changes nothing. Take the template from freshly fetched `origin/dev`, never from the branch checkout. Plain words and diagrams, no code, paths or symbol names, no `<details>` folds, no tables outside slot 12.
- **Generated, never drawn by hand.** The `pr-description` skill, when installed (else by hand in the same shapes), prints the skeleton from the diff with one fixed diagram shape per slot, so the same change draws the same diagram: the request path, data model, migration, env, endpoints and pipeline, plus the Touches line. An agent writes only the judgment lines (decisions, origin, hostile cases, event flow, state machine, business logic, load). What nobody measured stays visible: `not labelled`, `not measured`, `not traced`.
- **Diagrams.** Always horizontal (`flowchart LR`, an `erDiagram` or `stateDiagram-v2` with `direction LR`), the request path one diagram however wide. Nodes named by what they do in plain words. No theme or `style` lines; what changed carries `classDef added fill:#3fb95033,stroke:#3fb950,stroke-width:2px`, `classDef changed fill:#d2992233,stroke:#d29922,stroke-width:2px` or `classDef removed fill:#f8514933,stroke:#f85149,stroke-width:2px,stroke-dasharray:4`, with the template's legend line under it. The Request path shows the caller, every middleware and gate in order, the handler, each service, port, store and adapter, then the status and the total; every step has its ms and every arrow says what crosses it, from the trace span, else the code, else `not labelled`. The Data model shows the changed tables plus one foreign key away, keys and marked columns only. A status added, removed or moved gets a State machine.
- **Show the real trace.** Slot 10 holds one gantt per changed or added procedure from a real run: the integration suite records a span per request, oRPC step and pg query into `packages/testing/trace-results/`, and `node packages/testing/scripts/trace-report.ts packages/testing/trace-results [<baseline dir>] --gantt <procedure>` prints it (row and advisory locks as red bars, writes as light bars, statements new since the baseline prefixed `+`). "Queries and indexes" lists index per new query, N+1 and queries added per request. CI's "Backend trace report" job summary compares every procedure against `dev` on each PR.
- **No CI checklist or test count in the description.** "typecheck clean", "159/159 passing", "pipeline green" or a list of added test files is noise a reviewer can see for themselves. Only write down what CI cannot show: the hostile cases tried, a sandbox call against a vendor, a data migration run by hand.
- **No sensitive/internal data in titles, descriptions, or commits** - they are the public record. Bare ticket key (`ABC-45`), never the URL; no internal links, hostnames, secrets, PII. When in doubt, leave it out.
