# Git and delivery

Detail for the delivery lines in `conventions`. Read this before committing, opening a PR, or writing a commit message.

- **Conventional commits, enforced** (commitlint on commit + CI). Types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `perf`. The scope is a workspace-derived `scope-enum` (module dirs, apps, plus `ci`/`deps`/`rules`/`repo`/`tooling`); an unlisted scope fails - check with `pnpm commitlint --from HEAD~1` or omit the scope. `feat(wallet): atomic debit command port`
- **Subject must start lowercase** (`subject-case`), acronyms included - write `feat(pam): kyc status filter`, not `KYC`. This applies to the **PR title too**: squash-merge derives the `dev` commit message from the PR title, which local commit hooks never lint - an uppercase title lands a failing commit on `dev`.
- **One ticket = one PR, however big.** Never split a ticket by size; splitting is a person's call, made by creating sub-tasks. Stage files explicitly; never `git add -A` with foreign changes in the tree.
- **No changeset in a feature or fix PR.** Do not run `pnpm changeset` or add `.changeset/*.md` alongside code. Changesets are written in their own PR once the work has landed and the release is being prepared, so the bump and summary describe the final state, not every iteration.
- **Green before review:** `pnpm verify` passes; `pnpm regen` after any contract/schema change.
- **Branch off `dev`; never commit directly to `dev`/`stage`.** Promotion chain `dev -> stage` + release tags. Never push without an explicit per-action confirmation, except the branch `/ship` opens its PR from.
- **PR description is a review pack** (`docs/standards/skills/delivery.md` step 9): the bare ticket key, "How it was checked", then only the sections of `.github/pull_request_template.md` whose trigger fires; delete the rest and do not invent others. A reviewer reads generated artifacts, not the diff, so three of them stay open right under "How it was checked": "Request path", "Data model" and "Trace"; every other section is collapsed. Take the template from freshly fetched `origin/dev`, never from the branch checkout. Plain words and diagrams, no code, paths or symbol names. Budget: the words that show before anything is expanded fit one screen (about 1500 characters, the open diagrams aside), and each collapsed section fits one screen (about 1500 characters plus its diagram); a section's detail goes into its diagram or table, not paragraphs. Over budget, dropped review findings move into a collapsed `<details>`.
- **Diagram the flow.** A PR that adds or changes a flow across components (a request path through gates and ports, a state machine, an async job or webhook, a new module, port or table relation) fills the template's Architecture diff, Business logic or Endpoints section with a horizontal Mermaid diagram, nodes named by what they do in plain words, not by file or function: the changed nodes plus one neighbour each side, max ~10 nodes, refusal and failure branches included. "Request path" and "Data model" are the two that cut nothing (next rule). A node stays only when cutting it would leave the reviewer asking where something comes from or goes. Keep every branch the change adds or changes, a removed step, and each boundary between systems the change crosses. Cut unchanged nodes past one neighbour on each side, edge labels that repeat a node's name, commands, flags and variable names inside nodes (the diff has them), and the legend when the section already says what the colours mean. No theme or `style` lines; the only styling is a translucent fill and a border on what changed, readable on a light and a dark page: `classDef added fill:#3fb95033,stroke:#3fb950,stroke-width:2px`, `classDef changed fill:#d2992233,stroke:#d29922,stroke-width:2px`, `classDef removed fill:#f8514933,stroke:#f85149,stroke-width:2px,stroke-dasharray:4`. No flow (docs, deps, a one-file fix): delete those sections.
- **Show the whole path and the tables.** A PR that changes a route, procedure, middleware, service or query fills "Request path" with the whole path of the changed request, unchanged hops included: the caller, every middleware and gate in the order it runs, the handler, each service and port, then the database, cache, queue and adapters, taken from the procedure's real middleware chain and its trace spans. It fills "Data model" with an `erDiagram` of the tables that flow reads and writes plus every table one foreign key away, relations, keys and touched columns included. In both, what the change adds, changes or removes carries the `added`, `changed` or `removed` class (a table as `ledger_entries:::added`, a column with "new" or "changed" in its comment); in a `sequenceDiagram` the added steps sit inside `rect rgba(63, 185, 80, 0.15)`.
- **Show the real trace.** A PR that changes a route, service or query fills the template's Trace section from a real run, not from memory: the integration suite records a span per request, oRPC step and pg query into `packages/testing/trace-results/`, and `node packages/testing/scripts/trace-report.ts packages/testing/trace-results [<baseline dir>] --gantt <procedure>` prints a mermaid `gantt` of one request per status (the happy path and each refusal), row and advisory locks as red bars, writes as light bars, and statements new since the baseline prefixed `+` when one is given (record it by running the same suite on `dev` first, or download the `trace-spans` artifact of the last merge-queue run). Then, in "Queries and indexes", a list of performance conclusions: index per new query, N+1, queries added per request, sequential queries that could run in parallel, repeated reads. CI's "Backend trace report" job summary compares every procedure against `dev` on each PR.
- **No CI checklist or bare test-file list in the description.** "How it was checked" gives the checks result for the head SHA and names each test by the behaviour it proves; "typecheck clean", "159/159 passing", "full gate passed" or a list of added test files is noise a reviewer can see for themselves. Beyond that, only write down verification CI cannot show: a manual walkthrough, a sandbox call against a vendor, a data migration run by hand.
- **No sensitive/internal data in titles, descriptions, or commits** - they are the public record. Bare ticket key (`ABC-45`), never the URL; no internal links, hostnames, secrets, PII. When in doubt, leave it out.
