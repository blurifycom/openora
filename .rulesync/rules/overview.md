# AGENTS.md

Canonical brief for AI agents (Claude Code, Copilot, Codex, Cursor, etc.) - humans too. Per-tool files (`AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, `.codex/config.toml`, plus the subagent + command mirrors) are generated by [rulesync](https://github.com/dyoshikawa/rulesync) from the single source in `.rulesync/` (`rules/`, `subagents/`, `commands/`, `mcp.json`). Edit the source, then run `pnpm sync:agents`. Never hand-edit generated files.

Apply all sibling rules: `conventions` (code standard - philosophy, naming, types, functions, comments, testing, errors, deps, git, with examples), `clean-architecture` (add-on layering, DI, ports & adapters, shared helpers), `messaging-and-microservices` (the three async seams, command vs event vs job, outbox, service manifest), `db-conventions` (SQL / Drizzle - snake_case, timestamptz, keys, indexing, migrations).

## Mission

Open-source, headless, plugin-based, AI-native igaming platform. Anyone clones the repo and extends it with their own modules, plugins, and adapters; the frontend lives in their consumer repo. The default backend is fully featured (auth, wallet, lobby, chat, bonus, compliance, backoffice, CMS, aggregator). Nothing consumer-specific lives here.

## Architecture pillars

1. **Zod-first contracts.** Every shape is a Zod schema; types are `z.infer`'d, never hand-written. Cross-cutting schemas in `packages/core/src/contracts/schemas`; each add-on OWNS its route contract + req/res schemas in `src/contract/` (co-located with its service + router), module-local helpers in `schemas/`. `composeContract` (`@blurifycom/core/contracts`) owns only `health` - it is NOT an aggregator; the composition root (`tools/build-contract.ts` here; the consumer's entry when deployed) composes each enabled module's `/contract` slice into the one runtime `contract` the SDK client links against. ADR-0021/0025.
2. **oRPC + Hono.** oRPC owns route definition + Zod validation + OpenAPI emit; its `OpenAPIHandler` mounts on a Hono server (`@hono/node-server`, Bun-ready later). DI is a functional `Container` (`@blurifycom/core/server`) - typed-token factories, no decorators, no `reflect-metadata`. ADR-0009.
3. **Plugin host.** `definePlugin({ id, dependsOn, register })` is the only way new functionality enters. The consumer owns the API entry; overlays live in `apps/<name>/src/extensions/<name>/`; npm-published plugins use the same contract.
4. **Headless backend only.** Ships backend modules + contracts + SDK surface only. The frontend - components, styling, theme - lives in the consumer, which imports `@blurifycom/core/react` (hooks, typed client, auth, realtime). No UI packages ship here.
5. **Explicit > magic.** No auto-discovery, no decorator soup. Everything greppable; every wiring point a typed call.
6. **AI-friendly.** Every module has an `AGENTS.md`; every scaffold a slash command; every contract queryable via the MCP dev server (`describe-module`, `list-routes`, `query-openapi`) + the generated `docs/catalog.json`.
7. **Functional & declarative by default.** Pure functions, immutable data, composition over imperative mutation and stateful classes. A `class` only as a thin DI shell whose methods delegate to pure functions; no decorators, no inheritance for reuse. Full rationale + examples in `conventions` (§1, §4).

Headless: ships `@blurifycom/core` (domains + engine), the SDK, tooling. The API server lives in the consumer (`apps/api` removed 2026-06-22; reference frontend + page/block SDK removed 2026-06-09). `@blurifycom/core/react` is the supported frontend surface.

## Where does X go? (decision tree)

- **New business domain** (eg "tournaments") -> core add-on (ships free) or gated add-on (optional). `pnpm gen module <name>` creates `@blurifycom-addons/<name>` (own package.json, tsconfig, schema/schemas/service/router/plugin/contract). Registers in `extensions.config.ts` (no `kind` = core, `kind: 'addon'` = gated). Core: add its `/contract` slice to `tools/build-contract.ts`, tables use central migrations. Gated: conditionally merges its contract, owns its `drizzle.config.ts`. ADR-0021/0024.
- **Extend/override an existing add-on** -> overlay plugin in the consumer's `extensions/<name>/plugin.ts`. `/scaffold-plugin <name>`.
- **New HTTP route** -> the add-on's `src/router/index.ts`. `/scaffold-route <addon> <method> <path>`. Player routes resolve the caller from `x-user-id`; admin routes MUST be guarded (next).
- **Admin-only route** -> `plugin.ts` resolves `AdminGuard` (`c.get(ADMIN_GUARD)`, seeded by `createApp`) and passes it into the router; call `await adminGuard.assert(context)` as the handler's FIRST line (throws `ORPCError`). The single admin-enforcement point - never re-implement the role check.
- **New DB table** -> a Drizzle `pgTable` in the add-on's `src/schema/index.ts`; `pnpm regen`. Core schemas join central `packages/core/drizzle.config.ts`; gated own theirs. Datetimes are timestamptz (see Naming).
- **Reusable Zod schema** -> `packages/core/src/contracts/schemas/src/<namespace>.ts`. Add-on-local schemas in the add-on's `schemas/`.
- **Cross-add-on event** -> declare the payload in `domainEventSchemas` (`packages/core/src/contracts/schemas/src/events.ts`), emit via the `EventBus` (built in `plugin.ts` from `c.get(EVENT_BUS)`), subscribe in a plugin with `ctx.events.on(...)`. The bus is a facade over the `MESSAGE_BROKER` seam. ADR-0010; detail in `messaging-and-microservices`.
- **Frontend UI** -> NOT here (headless). Lives in the consumer over HTTP via `@blurifycom/core/react`.
- **New data hook** (eg `usePlayerWallet`) -> `packages/core/src/react/src/hooks/` + export (domain-specific hooks in that domain's `/react` subpath). The SDK must hand-write `useMemo`/`useCallback` for any stability-contract return (the consumer's React Compiler does not reprocess `node_modules`) - see `conventions` §7.
- **Operator config** (feature flags, brands, RG defaults per geo) -> a `platform-config.yaml`/`.json` consumed by `loadPlatformConfig()` (`@blurifycom/core/server`), validated by `PlatformConfigSchema`, bound via `PLATFORM_CONFIG`. No admin UI in v1; edit the file. ADR-0013.
- **Third-party integration** (PSP, KYC, aggregator, chat) -> define the adapter interface + token (`createToken<Adapter>`) in `packages/core/src/contracts/adapters/src/<category>.ts`, implement under `packages/addons/<name>/adapters/<vendor>/`, bind in `plugin.ts` via `ctx.provide(TOKEN, () => new Impl())`. Never inline.
- **Background task** -> the `JOB_QUEUE` seam: resolve in `plugin.ts`, `enqueue(queue('name'), payload, { idempotencyKey, delayMs, attempts, backoff, orderingKey })`; a worker overlay registers the handler via `ctx.jobs.worker({ queue, schema, handler, onDeadLetter })`. At-least-once - handlers idempotent (DB guard for money). ADR-0014.
- **Live client push** (chat, PvP state, live odds, big-win feed) -> the `REALTIME_TRANSPORT` seam + an oRPC `eventIterator(...)` served as SSE; client consumes with `useEventStream` / `useChatStream`. Client-facing only, separate from `MESSAGE_BROKER`. ADR-0007/0014; `chat` (in `@blurifycom/engagement`) is the reference vertical.

## Naming

Cross-cutting basics (kebab files, PascalCase types, `<Name>Schema` + inferred `<Name>`, predicate booleans, units in names) are in `conventions`. OSS-specific:

- Packages: `@blurifycom/<kebab>` (platform), `@blurifycom-addons/<kebab>` (add-ons - standalone under `packages/addons/<name>/`, imported by package name + read-only `/schema` subpath).
- Add-on role (`player`/`backoffice`/`platform`) is descriptive metadata, not a directory. An add-on exposes API only (no JSX). Public API = root entry + `/schema`; reaching internals is a lint error (`no-addon-internal-import`).
- oRPC routers: namespace by add-on (`wallet.transactions.list`).
- SQL / Drizzle identifiers (snake_case, timestamptz, keys, indexing, efficient queries, migrations) - see `db-conventions`.

## Dependency rules (two-layer enforcement, both in `pnpm verify`)

Two complementary gates, kept in sync: (1) **oxlint `oss-boundaries/*`** (`tools/oxlint-boundaries-plugin.mjs`) - fast per-edit string matching on import specifiers (runs via `pnpm lint` + the post-edit hook); (2) **dependency-cruiser** (`.dependency-cruiser.cjs`, `pnpm boundaries`) - the resolved whole graph, so it also catches transitive edges, re-export/barrel laundering, dynamic `import()`, and relative paths that dodge the prefix. ADR-0015.

- `packages/addons/**` may import `@blurifycom/core/{contracts,server,react}` + other add-ons' read-only `/schema`. NOT another add-on's root/internals (`no-cross-addon`) - communicate via events or contracts.
- A folded domain (`packages/core/src/<domain>` = any `core/src` dir except the `contracts`/`server`/`react` engine zones) may import engine zones + a sibling's read-only `/schema` only - never a sibling's internals (`no-cross-domain`). Couple via a command/adapter port, a domain event, or a shared contract through the composition root. ADR-0024/0025.
- `contracts` is isomorphic: imports only other contracts + Zod, never `server` or a module (`no-contracts-to-runtime`).
- `react` is browser glue: never imports `server` or an add-on (`no-react-to-runtime`).
- Engine zones (`contracts`/`server`/`react`) never import a folded domain (`no-core-to-domain`) or an add-on (`no-core-to-addon`). createApp is DI-driven; domains/add-ons are wired in only through the consumer's app (+ `@blurifycom/testing`). ADR-0021/0024/0025.
- Import the package/subpath entry, never a deep `dist/` path.
- No circular deps (`import/no-cycle` + `no-circular`). Break by extracting a shared package, inverting a dependency, or moving the type to contracts.

## Forbidden patterns

Cross-cutting bans (lint-enforced) live in `conventions`: `any` outside tests, `interface`, decorators, classes-for-reuse/inheritance/stateful-helpers, needless mutation, hand-written/duplicated types, import cycles, inline `fetch`/`axios`, bare `TODO`s. OSS-specific:

- Ad-hoc or duplicated Zod schemas in routers/services - schemas live in the add-on's `contract/`, `schemas/`, or core contracts; derive with combinators (`.pick/.omit/.partial/.extend/.merge`), don't re-type fields.
- Re-exporting types "to be nice" - import from where defined.
- A per-add-on `package.json` importing `@blurifycom/modules` - each add-on is standalone.
- SQL anti-patterns (bare `timestamp()`, CamelCase identifiers, hand-edited migrations) - see `db-conventions`.

## How-tos

| Task                           | Steps                                                                                                                                                                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Add a module                   | `pnpm gen module <name>` -> fill the `// AGENT: implement here` regions, leave wiring -> `pnpm regen && pnpm verify`.                                                                                                          |
| Add an overlay plugin          | `/scaffold-plugin <name>` -> in `register(ctx)`: `provide`, `routers.add`, `slots.fill`, `events.on`, `mcp.tool`. Override an adapter: `ctx.provide` your impl + load after the default in `extensions.config.ts` (last wins). |
| Add an oRPC route              | `/scaffold-route <add-on> <method> <path>` - import schemas, no ad-hoc.                                                                                                                                                        |
| Extend the DB schema           | edit a `pgTable` in `src/schema/index.ts`; `propose-table-change` first (collisions); `pnpm regen`. Read another add-on's tables via `@blurifycom-addons/<name>/schema`.                                                       |
| Consume from a downstream repo | `pnpm create:app ../my-igaming --name my-igaming`. See `docs/downstream-consumer.md`.                                                                                                                                          |

### Run locally

```
pnpm setup:agent   # first time: docker + db + mcp + summary
pnpm dev           # turbo dev (docs, mcp)
pnpm regen         # openapi emit + drizzle-kit generate + sdk regen + catalog
pnpm seed          # demo data (idempotent; admin@oss.dev / password123; flags --players/--admin-email/--admin-password)
pnpm boundaries    # whole-graph boundary + cycle gate
pnpm verify        # typecheck + test:unit + lint + module-shape + boundaries
```

Docker is library-first: `docker compose up` starts only postgres; apps run on the host via `pnpm dev`. The API server lives in the consumer - this repo ships packages, not a runnable server. Open a PR only on green `pnpm verify`; CI adds a no-drift check (re-runs drizzle-kit + the catalog generator, fails on an uncommitted diff). The pre-commit hook runs `pnpm boundaries`.

## Definition of done - audit every new action

Every new **state-changing action** (mutation route, admin op, money/KYC/config/withdrawal change) MUST leave an entry in the append-only, sha256 hash-chained `audit` add-on. The audit trail never lags the feature. Two decoupled-first ways:

1. **Domain event (preferred).** Emit after the DB commit, declare the payload in `domainEventSchemas` (`@blurifycom/core/contracts/events.ts`), and add the topic to `SUBSCRIBED_TOPICS` in `packages/addons/audit/src/plugin.ts`.
2. **Direct record (no natural event).** Resolve the `AUDIT_WRITER` port in `plugin.ts` and call `record({ actorId, actorType, action, resourceType, resourceId, before, after, ip, ... })` - for admin actions / non-event outcomes.

Capture actor (player/admin/system), resource, and before/after on mutations. No audit entry = not done. Pure reads, docs, tests, chores need none.

## Agent roster

For **platform development** (this repo). Consumer igaming agents ship separately in `tools/templates/consumer/__dot__rulesync/subagents/`.

| Agent               | When to use                                                    |
| ------------------- | -------------------------------------------------------------- |
| `expert`            | Fuzzy ask -> requirements + AC; regulatory/rules questions     |
| `dev`               | Implement a module/plugin/adapter from a given spec            |
| `module-author`     | Author a complete module end-to-end from the roadmap           |
| `plugin-author`     | Overlay plugin that extends without touching core              |
| `operator`          | Audit from an operator view; find launch blockers              |
| `contract-reviewer` | Diff for breaking changes, boundary violations, schema drift   |
| `security-reviewer` | Money/authz/tenant/secret-PII/auth-flow risks in changed files |
| `qa`                | Playwright E2E; Chrome DevTools debug; bug triage              |
| `docs`              | Rewrite prose docs to match code, then run `pnpm sync:agents`  |

**Delegation is mandatory.** When a task matches a roster agent, spawn THAT agent (`Task` with `subagent_type: <name>`) - not `general-purpose`/`claude`. Each is pre-scoped (tools + model + brief), so cheaper and more accurate. A `preToolUse` hook (`guard-subagent.mjs`) rejects a generic Task that fits a roster agent. `general-purpose` is only for cross-cutting work no roster agent covers.

## Conventions for agents specifically

- Read this file, then the sibling rules (`conventions`, `clean-architecture`, `messaging-and-microservices`, `db-conventions`), then the module's `AGENTS.md`, then ADRs. Don't reopen settled questions.
- The `oss-dev` MCP server is in `.mcp.json` (stdio, pre-approved via `enabledMcpjsonServers`). Use it for read-only inspection (`read-agents-md`, `list-modules`, `describe-module`, `list-routes`, `list-extension-points`, `query-openapi`, `get-drizzle-schema`, `propose-table-change`, `schema-get`, `docs-search`, `db-query-readonly`) - faster than grep, reflects current state. Write ops (`scaffold-*`, `regen`, `run-verify`) call the same scripts humans use.
- Before a route: `query-openapi` (does it exist?). Before a table: `propose-table-change`.
- After any change: `pnpm verify` for the affected package; fix failures before continuing.
- Wire every state-changing action into the audit log before calling it done (above).
- Small PRs scoped to one module; cross-module changes need human approval. Don't commit unless asked; don't push without confirmation.
- ASCII only in code; short dashes (-) only, never long dashes.
