**`REALTIME_TRANSPORT` is now Redis Pub/Sub-backed and requires `REDIS_URL` in every deployment.** The wallet balance stream (and every other realtime consumer - chat, KYC status) previously fanned out only to subscribers on the same process: a deposit webhook landing on one API instance never reached a player whose SSE connection was held open on another. That worked in local dev and single-pod staging and failed silently behind a real load balancer. `RedisPubSubRealtimeTransport` (`packages/core/src/server/kernel/redis-pubsub-realtime-transport.ts`) fixes this - every replica subscribes over Redis Pub/Sub, and `createApp` auto-binds it exactly like `MESSAGE_BROKER`/`JOB_QUEUE`/`CACHE`/`RATE_LIMITER` do on `REDIS_URL`. See ADR-0031.

**Breaking: `InProcessRealtimeTransport` is deleted, not kept as a fallback.** `REALTIME_TRANSPORT` joins `assertDurableSeamsBound` - a deployment without `REDIS_URL` now fails to boot with an actionable error instead of silently degrading to per-process delivery. Every test tier (`bootTestApp` and the `.int.test.ts` files that exercise realtime delivery) binds the same Redis-backed driver production does, following the same rule ADR-0032 already applied to the other four seams. An operator upgrading must set `REDIS_URL` if they had not already (most already do, for the other four seams); an overlay (eg Ably) rebinds `REALTIME_TRANSPORT` exactly as before.

Pub/Sub, not Streams: this is fire-and-forget UI push, not a durable inter-service event, so the outbox and `MESSAGE_BROKER`'s ack/retry machinery deliberately do not apply. A message published while a client is briefly disconnected is simply lost - unchanged from before, and safe because a realtime channel has always carried a change _signal_, never the state itself (see `docs/modules/wallet.md`): the client refetches over HTTP on every (re)connect rather than trusting it caught every frame. Channels are namespaced by `SERVICE_NAME`, the same durable per-deployment identity `RedisStreamsBroker` already uses for its consumer group, so two deployments sharing one Redis do not cross-deliver.

`RealtimePresence`/`getOnlineUserIds` stay replica-local (no shared Redis SET/TTL store yet) - correct for a single instance, an undercount (never wrong-direction) on a multi-instance deployment, a disclosed and deliberate gap rather than a silent one.

**Fixes a related silent-outage bug in `RedisStreamsBroker`** (`MESSAGE_BROKER`'s consumer loop): once a consumer group's handshake succeeded, the loop never retried it on a later error. If the underlying stream key was ever lost (a flush, an expiry, an operator mistake), every subsequent read threw `NOGROUP` in a permanent loop with no recovery short of restarting the whole process - and this now matters more, since realtime shares the same Redis. The loop now re-runs the handshake after any non-`BUSYGROUP` error, so `MKSTREAM` recreates the stream and group on its own.
