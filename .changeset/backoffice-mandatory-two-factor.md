---
'@openora/core': minor
---

Mandatory Backoffice 2FA and device-bound admin sessions, off by default and switched on per operator through `PlatformConfig.adminSecurity`.

- New `ADMIN_SECURITY_POLICY` port (`@openora/core/contracts`), resolved optionally by `AdminGuard`, so mandatory-2FA and session-fingerprint checks run on every admin route from a single place. The identity module binds it; leaving the module out keeps the guard's previous behaviour. Two new `AuthGuardReason` values: `two_factor_required`, `session_fingerprint_mismatch`.
- `PlatformConfig.adminSecurity` (`requireTwoFactor`, `bindSessionToDevice`, `trustedDeviceDays`, `ipChangePolicy`, `twoFactorLockout`). `requireTwoFactor` and `bindSessionToDevice` default to `false` and `ipChangePolicy` to `off`, so an existing deployment upgrades with no behaviour change; whether Backoffice 2FA is mandatory is a licensing decision the operator owns.
- `verify2fa` accepts `trustDevice`, forwarded to better-auth's `trustDeviceMaxAge` window (`trustedDeviceDays`, default 30). A grant is also recorded in the new `admin_trusted_device` table, and a device skips the second factor only while both the better-auth cookie and an unrevoked row exist - which makes the trust window listable, auditable and revocable by the user or an admin holding `sessions:revoke`.
- `bindSessionToDevice` ties an admin session to the browser it was issued to. A mid-session User-Agent change (or an IP change, per `ipChangePolicy`) revokes the session and the trust that device held, so the next login runs a full second factor. `ipChangePolicy: 'country'` resolves through `GEO_IP_ADAPTER` and degrades to `off` when no adapter is bound.
- Consecutive failed second factors lock the account after `twoFactorLockout.maxAttempts`, counted in new `user` columns of their own so a 2FA lockout never consumes the password-login budget. The pending user is resolved from the two-factor verification row, so the lockout follows the account rather than the browser.
- `UserSchema` gains a required `twoFactorEnabled`. `SessionItem` gains `lastSeenAt`, `deviceLabel`, `browser` and `os`; `session` gains a `last_seen_at` column written by the admin guard, so "last activity" no longer depends on better-auth's 24h `updateAge` bookkeeping.
- New routes: `sessions.listAll` (every active session across accounts, `sessions:view`) and an `adminSecurity` namespace (`status`, `trustedDevices`, `revokeTrustedDevice`, `revokeUserTrustedDevice`). `sessions.revokeMine` now refuses the caller's current session.
- `twoFactor()` is configured with `otpOptions.sendOTP`, delivered through a transport-agnostic hook the identity module binds - core names no delivery vendor.
- New audited events: `identity.2fa.verified`, `identity.2fa.failed`, `identity.2fa.lockout.triggered`, `identity.2fa.enrollment_blocked`, `identity.session.fingerprint_mismatch`, `identity.trusted_device.added`, `identity.trusted_device.revoked`. `identity.2fa.enabled` and `identity.2fa.disabled` gain a required `method` and are bumped to payload version 2.
- Backup codes are a working recovery path, not just an enrolment artefact: `verify2fa` takes a `method` (`totp` | `backup_code`) and spends a code through better-auth, `adminSecurity.status` reports `backupCodesRemaining`, and `regenerateBackupCodes` replaces a spent set behind the account password. The `code` field widens to 11 characters, the length better-auth actually issues.
- `adminSecurity.trustCurrentDevice` grants the trust window from inside an authenticated session. better-auth mints its trust cookie only on the sign-in leg of a challenge, so the route replays that leg behind the account password and a fresh factor rather than forging a cookie of its own.
- `adminSecurity.resetUserTwoFactor` (`admin:update`) returns an account to the unenrolled state - the recovery path once an authenticator is lost along with its backup codes - and revokes that account's trust grants and live sessions with it.
- Revoking a trusted device no longer ends the session the revoke was issued from; the caller stays signed in and faces a full second factor on the next login, matching `sessions.revokeMine`.
- `identity.2fa.enabled` is emitted only for the enrolment challenge. It previously fired on every successful sign-in.
- New audited event: `identity.2fa.backup_codes_regenerated`, `identity.2fa.reset`.
